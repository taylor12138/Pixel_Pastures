## 上下文

Godot 工程位于 `pixel-farm/`。项目已经实现 `EconomyManager`、`InventoryManager`、`LevelManager`、`GameManager` 和 `EventBus`，并由 `EconomyManager` 提供商品列表、可售库存、价格、预校验和交易结果字典。现有 `InventoryPanel` 已建立全屏 `Control` 面板、事件驱动刷新、`ui_input_block_changed` 和不暂停时间的输入阻塞约定。

当前缺口是玩家无法通过正式 UI 使用经济能力。商店面板需要横跨经济、库存、等级解锁、场景输入和 UI 状态，同时兼容 480×320 视口、占位视觉和未来商店场景复用。

## 目标 / 非目标

**目标：**

- 提供购买/出售双 Tab 的商店面板和可复用商品行。
- 以 `EconomyManager` 为交易、价格与列表数据的唯一权威。
- 提供商品详情、锁定状态、数量预设、最大数量、总价、余额与结果反馈。
- 使用事件驱动方式刷新交易结果、金币、库存、解锁和读档状态。
- 复用背包面板的输入阻塞约定，并保持游戏时间继续运行。
- 提供独立测试场景并接入现有回归体系。

**非目标：**

- 不实现常驻金币 HUD、正式商店美术、店主对话或移动端触控适配。
- 不新增折扣、季节商品、一键出售全部或物品使用逻辑。
- 不修改价格表、库存结构、交易回滚、经验规则或等级解锁算法。
- 不引入统一 `UIManager`；多面板互斥留给后续系统菜单阶段。

## 决策

### 1. ShopPanel 只编排，Manager 保持数据权威

`ShopPanel` 通过 `get_shop_items()`、`get_sellable_inventory_items()` 和 `get_shop_item_info()` 构建视图，通过 `can_buy_item()` / `can_sell_item()` 更新按钮状态，通过 `buy_item()` / `sell_item()` 提交交易。UI 禁止直接写 `GameManager.gold`、`InventoryManager._slots` 或复制价格、可售类型与解锁规则。

原因：经济层已经实现完整校验和回滚。UI 保持无业务写入可以避免双重扣费、部分入包和显示数据漂移。

### 2. 一个 ShopItemRow 支持两种模式

`ShopItemRow` 使用 `BUY` / `SELL` 模式分别接受购买列表和出售列表字典，统一显示类型占位、名称、单价、拥有/库存数量、选中和锁定状态。行组件只发射 `row_clicked(item_id)`，不执行交易。

原因：两类行的布局和交互高度相似，共用组件可保持视觉与选择行为一致；交易差异集中在面板层更容易测试。

### 3. 面板保存当前列表数据的副本，不缓存业务规则

面板可保存当前 Tab 的商品字典副本，供详情和局部刷新定位使用，但价格、数量、解锁与可交易性在每次刷新时重新查询 Manager。交易成功、金币变化、解锁变化和读档后不得依赖旧字典继续判断。

原因：字典副本适合 UI 渲染，但跨交易或升级后会过期。重新查询公开接口可以保证显示与权威状态一致。

### 4. 数量先按资源上限收敛，再用 EconomyManager 最终校验

购买最大值取 `floor(gold / unit_price)` 与 `InventoryManager.get_addable_count(item_id)` 的较小值；出售最大值取当前聚合库存。预设数量 1/5/10 和“最大”均夹取到 `0..max`，随后调用 `can_buy_item()` 或 `can_sell_item()` 决定确认按钮和提示。

原因：上限计算改善交互体验，最终仍由经济层校验可避免 UI 规则与业务规则分叉。单价无效、锁定或最大值为 0 时数量归零并禁用确认。

### 5. 交易提交以同步返回值反馈，事件负责跨系统刷新

`confirm_transaction()` 立即使用返回字典展示成功或失败消息；`transaction_completed`、`transaction_failed`、`gold_changed`、`inventory_changed`、`crop_unlocked`、`unlocks_changed` 和 `game_loaded` 用于同步其他观察者与外部状态变化。

同一次交易的多个信号可能连续到达，因此刷新方法必须幂等。成功后购买模式刷新对应行和可买性；出售库存归零时重建出售列表并清空选择。

### 6. 复用 InventoryPanel 的输入阻塞模式

`ShopPanel` 使用全屏遮罩和 `ui_input_block_changed(true/false)`，通过 `setup(context = null)` 接受可选场景上下文。打开、关闭方法保持幂等，信号只在 `_ready()` 连接一次，默认不设置 `SceneTree.paused` 或暂停 `TimeManager`。

在田园临时入口或商店场景中，由宿主根据统一 UI 锁阻止玩家移动、E 交互、农田点击和调试键。后续若多个面板同时存在，宿主必须避免关闭一个面板时提前解除另一个面板的锁。

### 7. 购买列表按能力展示，锁定项保留

购买 Tab 完整展示 `EconomyManager.get_shop_items()` 返回的 `seed`、`consumable` 和 `decoration`。未解锁种子保留在列表中并可查看详情，但数量控件和确认按钮禁用；出售 Tab 只展示聚合后数量大于 0 的收获物。

原因：保留锁定商品能向玩家传达升级目标，而出售空库存行没有操作价值。

### 8. 先提供独立测试入口，再接入正式商店场景

新增 `test_shop_panel.tscn` 使用真实 Autoload 验证逻辑与节点状态。面板同时支持在现有 `farm.tscn` 挂载临时入口；独立 `scenes/shop/shop.tscn` 可使用占位背景和店主节点，不依赖正式美术。

## 风险 / 权衡

- [经济与库存信号连续触发导致重复刷新] → 刷新接口保持幂等，普通变化优先局部刷新，出售归零、解锁和读档才全量重建。
- [关闭商店时错误恢复其他系统持有的输入锁] → 宿主保存打开前状态；本期至少保证开关幂等，并在测试中覆盖已禁用状态的恢复。
- [当前商品在刷新后消失，详情持有失效数据] → 每次刷新按 `item_id` 重新定位；找不到时清空选择和数量。
- [金币或容量变化使已选数量过大] → 每次 `gold_changed`、`inventory_changed` 和交易完成后重新计算最大值并收敛数量。
- [同步返回和 EventBus 同时显示两次反馈] → 面板统一通过一个结果处理函数去重，事件回调只刷新状态或识别相同结果。
- [480×320 下列表和详情拥挤] → 主窗口控制在 440×288，列表使用滚动容器，详情文本允许换行和截断。
- [缺失商品元数据或未知类型导致节点报错] → 名称回退 `item_id`、类型回退灰色、描述回退空文本，所有字典字段使用默认值读取。

## 迁移计划

1. 扩展 `EventBus` 商店 UI 信号，不修改现有信号签名。
2. 新增 `ShopItemRow` 与 `ShopPanel` 场景和脚本。
3. 新增独立商店测试场景并接入回归运行器。
4. 在田园场景增加临时入口，或新增占位商店场景挂载面板。
5. 完成 480×320 手测和现有 PRD1-11 回归验证。

本变更不修改存档 schema。回滚时可移除新增 UI、挂载点和商店 UI 信号，经济与库存数据保持兼容。

## 开放问题

- 正式商店入口最终采用进入场景自动打开还是与店主交互打开，由 PRD17 场景美术与 NPC 接入阶段确定。
- 多面板互斥和输入锁引用计数由后续统一 `UIManager` 设计处理；本期沿用现有单面板约定。
